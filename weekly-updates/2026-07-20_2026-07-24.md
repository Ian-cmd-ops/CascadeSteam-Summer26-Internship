## Completed

### Backup automation (Outcome 1)

Deployed an automated backup system: restic to an SFTP repository on the NAS,
reached over a Netbird overlay tunnel. Chosen against the actual constraint —
the WAN sits behind an ISP modem in router mode with a changing public IP, so
inbound WireGuard is unreliable and an outbound-dialing overlay is the only
transport that stays up.

Discovered no schedule existed. `crontab -l` was empty and
`systemctl list-timers --all` showed only `dpkg-db-backup`. Every snapshot in
the repository had been triggered manually; the last was 2026-07-21. The daily
cadence described in the design had never been created.

Built a systemd timer and service:

- `OnCalendar=daily`, `RandomizedDelaySec=1h`
- `Persistent=true` — required on a laptop, since a run scheduled while the
  machine is asleep is otherwise skipped silently rather than deferred
- Retention: `forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --prune`

**Verified off-network 2026-07-24.** Ran the full service from a foreign
network, not a snapshot listing — a listing only proves the tunnel is up, not
that a transfer completes over an unfamiliar NAT.

| Measure | Result |
|---------|--------|
| Tunnel to backup target | Direct peer-to-peer, not relayed |
| Exit status | 0 |
| Data captured | 26.947 GiB |
| Wall clock | 1m 37s |
| CPU time | 1m 58s |
| Peak memory | 8.7 GB (of 24 GB available) |

The scheduled run also fired unattended earlier the same night, before I
started anything manually — so the daily cadence is confirmed working, not
just the manual path.

**Fault found and fixed in the process:** the SSH host alias the backup used
resolved to a LAN address, so the transport would have failed from any
network but the home one. On the LAN this was invisible; every prior test had
passed for the wrong reason. Repointed to the overlay address, which is valid
from both inside and outside.

**Not yet complete:** failure is silent, and so is success. I only knew

### Multi-day network fault worked to root cause (Outcome 4)

A week of intermittent remote-access failures — connections timing out,
peers stuck connecting, services unreachable from one network segment but
fine from others — turned out to have a single root cause at the router.

The router ships with a default configuration entry that advertises itself
as an IPv6 gateway on every network segment. It had no IPv6 upstream: no
address, no route out, nothing. Clients believed the advertisement,
installed a default IPv6 route into a black hole, and every service that
prefers IPv6 name resolution hung on fresh connections.

What made this hard: established connections survived and only new dials
failed — so every diagnostic restart broke a previously-healthy machine,
making the restart look like the cause. Several plausible-but-wrong
explanations were run down first (a VPN feature bug, per-host DNS
misconfiguration, firewall rules), each producing a partial fix that masked
the real fault.

Worked by layer with what was ruled out logged at each step: DNS sinkhole
entries checked and cleared, firewall chains read, IPv4 vs IPv6 paths
tested separately (`curl -4` succeeded where `curl -6` failed — the
deciding evidence), then the router's IPv6 state read directly: neighbor
discovery active on all interfaces, no prefix delegation, no global
address, no default route, empty v6 filter table.

Fix was one line — disable the neighbor discovery entry — which repaired
every device on the network at once, including machines never touched
during debugging. Verified afterward from a second off-site network: full
mesh connected, backup target reachable at 0% loss.

Also documented the correct future path: if IPv6 is ever wanted, the v6
firewall gets written first, because the current empty filter table would
expose every host directly.

### Remote access failure discovered under real conditions (Outcome 4)

Attempted to reach the environment from an off-site network. Two of four peers
were absent from the mesh, including the backup target — meaning off-network
backup was non-functional and nothing had reported it.

The routing peer was reachable but unusable: SSH refused, because Debian
defaults to `PermitRootLogin prohibit-password` and no key had been installed
at build time. A gateway with no login path is not a gateway.

Resolved by pushing a key through the hypervisor. `ssh-copy-id` cannot
bootstrap this case — with password auth disabled there is no path to
authenticate the copy.

**The finding that matters:** the setup had never been verified from
off-network. LAN success does not prove remote access works, and both faults
were only visible from outside.

### Security boundary enforced (Outcome 3)

Identified that the overlay routing peer had been running on the same
hypervisor as an adversary-simulation lab — intentionally vulnerable target
systems on an isolated bridge.

**Risk/Impact:** a container escape from the routing peer, or a guest escape
from a target VM, reaches a host dual-homed into the production overlay.
Compromise of a disposable training target becomes lateral movement into the
credential store, the git server, and the backup repository.

Moved the routing role to a host with no lab workloads and documented the
exclusion so it does not get re-introduced.

### Git server access (Outcome 3)

Found that git-over-SSH had never worked. The hostname resolved to the reverse
proxy rather than the git server, and the git server's container published
only its HTTP port — no SSH mapping existed at all, so no key would ever have
authenticated.

Published the SSH port, configured client-side host aliasing with
`IdentitiesOnly`, and verified authentication.

## Blockers

**Storage capacity.** The hypervisor's thin pool is at 79% with 197 GiB
provisioned against a 141 GiB pool and 16 GiB of free extents. One volume is
at 99.91%. Autoextend was enabled but there is not enough free space for it to
matter — if the pool fills, every volume on it goes read-only simultaneously.
Needs either a capacity decision or a data migration; not something I should
decide alone.

**Recovery credentials.** Backup scope now includes the administrative home
directory, so the repository credentials are captured. That does not solve
recovery: the passphrase is required *before* the repository can be opened to
read the backed-up copy. The credentials still need to exist somewhere the
source machine is not. Needs an escrow decision — and the obvious internal
candidate runs on hardware in the same building as the backup target, so it
covers device loss but not site loss.
