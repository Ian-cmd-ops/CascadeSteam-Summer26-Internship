# 2026-09-06 — rsync exit 23 was treated as failure; snapshots discarded

## Symptom

ntfy push "Laptop backup FAILED / rsync exit 23 via ian@10.0.10.X" on a
manual run at home over LAN. The transfer itself completed (all readable
files landed in the work dir) but the script took the FAIL branch, logged
FAIL, and the EXIT trap deleted the work dir. No snapshot promoted.

Earlier the same evening the older `pull-backup.sh` tree showed the same
pattern: two weeks of "rsync failed or connection dropped mid-transfer"
lines in its log that were all exit 23, not network drops.

## Root cause

`laptop-backup.sh` accepted rsync exit 0 and 24 only:

    if [ "$rc" -ne 0 ] && [ "$rc" -ne 24 ]; then

rsync exit 23 means "partial transfer due to error". Here the errors are all
`Permission denied (13)` on the sender side: files and directories under
/home/ian that the `backupsrc` rrsync session cannot open. With Brave
running that is thousands of cache entries plus a handful of config dirs.
So any pull with the browser open exited 23 and was thrown away.

Exit 24 (vanished files) was already tolerated; 23 was the gap.

## Fix

1. `laptop-backup.sh`: accept 23 alongside 0 and 24. A 23 run continues
   through the change gate, promote, and prune. If it promotes, the normal
   snapshot line carries a suffix: `snapshot <stamp> via <target> (rsync
   exit 23, some files skipped; see .rsync-err and excludes)`. If the gate
   says no change, nothing is logged, same as a clean run, so an idle
   laptop with the browser open does not write a line every 15 minutes.
   No ntfy for the partial case; the exclude list is meant to absorb it,
   and the suffix is there to notice if the skip set grows.
2. `rsync-excludes`: add the paths that were failing so future runs should
   exit 0. All are browser-managed state, IPC sockets, or key material:
   `.ssh`, `ibus/bus`, `.local/share/nano`, `nautilus/scripts`,
   `Trash/expunged`, Brave `Local State`, `CertificateRevocation`,
   `PKIMetadata`, `Crowd Deny`, `blob_storage`, and the per-component
   version dirs `<id>/<n.n.n>/`.
3. Header comment on `rsync-excludes` said it deploys to
   `/root/.rsync-excludes`; the script and service use
   `/home/ian/.rsync-excludes`. Comment corrected.

`laptop-backup.service` keeps `SuccessExitStatus=0 24`. The script now exits
0 on a 23 run, so systemd does not see 23 and no unit change is needed.

## Verification plan (N100)

Copy the three files, then one manual run:

    bash /home/ian/rsync-snapshot/laptop-backup.sh; echo rc=$?

Expect `rc=0`. Then:

    tail -3 /home/ian/rsync-snapshot/logs/laptop-backup.log
    ls -l /mnt/backups/laptop/latest
    cat /mnt/backups/laptop/.last-check

Expect a `snapshot <stamp> via ian@10.0.10.X` line (with or without the
"(rsync exit 23, some files skipped ...)" suffix), `latest` pointing at that stamp, and
`.last-check` starting with `snapshot`. The "Laptop backed up" ntfy fires
only if this is the first snapshot of the day.

A second run right after should write `nochange` to `.last-check` and add
nothing to the log.

**unverified** at time of writing: whether the extension-version glob
`*/[0-9]*.[0-9]*/` is broad enough; new component ids appear as Brave
updates. If a snapshot line still carries the skip suffix, check `.rsync-err` on the
N100 for the new path and add it.

## Deployment note

The `~/pull-backup/` tree on the N100 is a separate, older script with its
own log at `/var/log/pull-backup.log`. It was patched the same way tonight
(23 accepted, excludes, ntfy added). Only `laptop-backup.timer` should be
enabled; if `pull-backup.timer` is also live, two pulls compete for the
laptop. Decide which tree is canonical and disable the other.
